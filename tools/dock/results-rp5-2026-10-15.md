## ARP conflict as the cause of the 10-08 "router goes silent to one client" (HYPOTHESIS, untested)
Cliff (~01:35): "how about our networking issues when unplugging and replugging the dock? Are they possibly some
similar type of issue?" Signature on 10-08 01:22 boot (HANDOFF 2026-10-08 02:20): NM full at 14 s, limited at
334 s; the device's ARP to the gateway answered, fusor/BONESAW/rizz/drip pingable, only the gateway silent to
ICMP/TCP/UDP from this client; `nmcli connection up ozma` fixed it in 3 s. That is what a stale ARP entry AT THE
ROUTER pointing at the dock/hub NIC's MAC produces after an undock: the device still resolves the router, Linux
hosts re-resolve .68 within seconds (unicast/broadcast probes), the router keeps sending .68's traffic to the
gone MAC, and a profile re-activation sends gratuitous ARP which updates it. The chain that makes the LAN learn
the wrong MAC is the 10-14 root cause (reference-rp5-wlan-route-arp-conflict): the dock NIC answers ARP for
.68 (arp_ignore=0), NM's conflict detection pulls the wlan0 subnet route, and from then on .68-sourced traffic
leaves through the dock port with the dock MAC. The hub ethernet (.47) was in use that week and the same handoff
has docked Dark Souls runs. If true: the wifi heal ladder (bsp-common 26-33, which caused the 10-05 dead wifi
after wake by PCIe-resetting the chip) treated this aftermath, and bsp-common 35 (arp_ignore=1/arp_announce=2)
removes the cause. Unknowns: whether the hub was attached at that 01:22 boot (record silent); why the router
stayed stale ~20 min (a Linux neighbor table would not; flow offload or a per-client IP binding would).
Test (rig only, after the overnight collect; ~5 min; sysctls restored by a trap):
old sysctls (arp_ignore=0, arp_announce=0) -> dock attached -> wait for NM's conflict line + the wlan0 /24 route
gone -> ping from .68 (ping -I 192.168.1.68 8.8.8.8 + fusor) -> on fusor `ip neigh show 192.168.1.68` = dock MAC?

## 10:35-10:50 ARP undock tests: ONE confirmation, one anomaly, one self-inflicted wifi outage. STOPPED.
Test 1 (scratchpad/arp-undock-test.sh, old sysctls 0/0 on all+default+both interfaces, dock NIC re-activated by usb
unbind/bind, then `ping -I 192.168.1.68` to the router and fusor):
- CONFIRMED: with arp_announce=0 the dock port's ARP requests carry the wifi address as sender; fusor's neighbour entry
  for .68 flipped to the dock MAC (6c:1f:f7:21:fe:a9). The route lookup put .68-sourced LAN traffic through the dock
  port (metric 100 beats wlan0's 600) WITHOUT any NM conflict: the conflict of 10-14 is a consequence, not the trigger.
- ANOMALY (seen once, not reproduced in test 2): after the unbind the device reached the gateway and fusor, fusor's
  pings to .68 were unanswered for 85 s although the device's ICMP counters say it received and answered them (16 in /
  16 out since boot, consistent with the 14 + 2 sent); the replies vanished between wlan0 and fusor. Not understood.
- The router's ARP entry did NOT stay stale for the device's own traffic: gateway pings from the device were fine
  within 3 s of the unbind (the device's ARP requests re-teach it, standard behaviour).
Test 2 (arp-undock-test2.sh, counters at both ends): run A (old sysctls, no re-activation, so no ARP request with
sender .68 was emitted = the poison step did not fire) and run B (shipped sysctls) both clean. The script's second
restore hung: `nmcli connection up ozma` associated in <1 s, then DHCP got NO lease for 45 s -> "ip-config-unavailable"
-> wlan0 disconnected; the ssh control session ran over the wifi link-local and hung with it; timeout killed the
script at 280 s. Recovery via the dock NIC (.72): `nmcli connection up ozma` + `arping -U -I wlan0 -s .68 .68`
during association -> lease in 2 s. INTERPRETATION (provisional): the router held .68 at the dock MAC (learned from run
A's .68-sourced pings through the dock port) and sent the DHCPACK to that MAC; a gratuitous ARP from wlan0 fixed it.
That is the 10-08 "router silent to one client" signature produced on demand: everything the router sends to the
wifi address goes to the other port's MAC until its entry is refreshed, and a profile re-activation (gratuitous ARP)
cures it. bsp-common 35 (arp_announce=2) removes the cause: the dock port never ARPs with the wifi address.
Decision: no more networking tests. Device back in the shipped state (sysctls 1/2, dock NIC bound, wlan0 .68 + /24
route, fusor -> .68 and the link-local both answer). Whether to cut the wifi heal ladder down is Cliff's call.
Lesson (Cliff 10:50: "we are going around in circles again aren't we?"): the first test already gave the usable
result; chasing the anomaly with a second instrumented run cost 15 min and a wifi outage. Stop at the usable result.
