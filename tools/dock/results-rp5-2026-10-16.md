## 12:3x-12:5x the sleep set itself (ground truth, kernel 43.2 on the device, drivers identical to 43)
- rpmh trace over one 120 s suspend: 95,004 ACTIVE-set messages (sugov:4/0/7 = cpufreq DDR/LLCC bandwidth BCMs SH0/SH4/ACV/MC0, ~500/s awake), ONE sleep-set write (MM0) and ONE wake-set write at the cluster PRE_OFF flush. A single suspend's trace is only the delta since the last flush, so:
- the RSC's sleep/wake TCS registers read directly (/dev/mem, drv-2 base 0x18220000, tcs-offset 0xd00, RSC v2.0, ver-2.7 offsets; names from /sys/kernel/debug/cmd-db): TCS2 (SLEEP) = MM0=0x40000000, TCS5 (WAKE) = MM0=0x60004001, every other sleep/wake/control slot EMPTY. The programmed sleep set is one display-bus BCM "off". cx.lvl, mx.lvl, mmcx.lvl, xo.lvl, ebi.lvl and every regulator keep their ACTIVE vote through suspend -> no cxsd, no aosd, no ddr self-refresh, ~96 mA.
- why (drivers/soc/qcom/rpmh.c, rpmhpd.c, clk-rpmh.c, qcom-rpmh-regulator.c in our tree): rpmh_flush programs a resource only when sleep_val != wake_val (is_req_valid); rpmhpd sends a sleep vote only for domains with an active-only peer and the sleep corner equals the active corner unless every consumer of the domain is off at suspend; clk-rpmh votes XO sleep == wake while any consumer keeps bi_tcxo prepared (remoteprocs adsp/cdsp hold it permanently, UFS ref_clk, both USB PHYs, mmc, DSI PLL); qcom-rpmh-regulator only ever writes RPMH_ACTIVE_ONLY_STATE (lines 203/205), so every enabled LDO stays on through suspend. This is the mainline state the 08-29 research note describes; the Odin 3 reached 31 mA on it by mitigation, never by aosd.
- rpmhpd state_synced=1 (its max-clamp is NOT in play); gcc + gpucc state_synced=0 (sync_state pending due to 3d6a000.gmu: the GMU is bound as an msm component) -> their boot-enabled clocks are never swept; va_macro 3370000.codec probe FAILED -110 at 10.4 s (the tx/rx/wsa macros waited 10 s on it, then probed) -> an audio bring-up bug on its own.
- trace detail (same window): cx.lvl and mx.lvl are voted to 0 by systemd-sleep's suspend path at 179.6367 s, 1.4 ms before the cluster flush -> the rails ARE released by the APSS (sleep == wake == 0 is why no TCS entry exists; the active vote 0 stands). What stands NON-ZERO at the flush: the DDR/bus BCMs SH0 0x6018a0b0, SH4 0x60005058, MC0 0x6024706d, ACV 0x60000008 (the CPU nodes' bandwidth path, voted by sugov), plus CN0, SN0, SN8, SN11, QUP0 (other ALWAYS-tagged consumers: UARTs/i2c/UFS/USB paths). sm8250.dtsi (upstream) gives the eight cpu nodes `interconnects = <&gem_noc MASTER_AMPSS_M0 0 &mc_virt SLAVE_EBI_CH0 0>` = tag 0 = QCOM_ICC_TAG_ALWAYS (icc-rpmh.c:92); sm8550/sm8650 upstream tag the CPU path QCOM_ICC_TAG_ACTIVE_ONLY. xo.lvl: no vote change in the window = XO stays on through sleep (remoteprocs/UFS/PHYs hold bi_tcxo; for aosd later).
- NEXT (ground truth, measurable before any counter): 0732 = tag the CPU paths ACTIVE_ONLY -> after one suspend the sleep TCS must show SH0/SH4/MC0/ACV = 0; then the ddr/cxsd counters; then the remaining ALWAYS consumers one by one (QUP0/CN0/SN*: the BT UART 888000, serial 998000, i2c, UFS, USB), then XO (subsystem-held), then the regulator sleep-set patches (pocknix 1046/1047 port) for the LDOs. Every step: TCS dump + counters + a long battery sleep for the mA.
